# Архитектура «Импульса» (релиз-кандидат 1.0)

Документ относится к рабочей ветке `develop`. `main` остаётся старой опубликованной основой до ручной приёмки кандидата.

## Точки входа

| Файл | Назначение |
| --- | --- |
| `index.html` | Семантический интерфейс, Canvas 480×720 и мобильные кнопки управления |
| `style.css` | Масштабирование игрового поля, адаптивность и оформление |
| `game.js` | Конфигурация, правила уровней, состояние кампании и координация игрового цикла |
| `game-storage.js` | Валидация настроек, рекорда и контрольной точки, восстановление игры |
| `game-ui.js` | Обновление DOM, панель настроек, экраны победы/поражения и статистика |
| `game-physics.js` | Физика шаров, обработка столкновений, геометрия направленных блоков и подвижные кирпичи |
| `game-bosses.js` | Страж и Реактор: движение, снаряды, фазы защиты и обработка урона |
| `game-effects.js` | Бонусы, временные усиления, частицы, волны и их жизненный цикл |
| `game-render.js` | Canvas-отрисовка и кэш статичных слоёв и спрайтов |
| `game-input.js` | Обработка ввода, запрос кадров и диагностика FPS |
| `tests/support/game-harness.cjs` | Общая изолированная среда Node.js для всех тестов |
| `tests/foundation.test.cjs` | Базовая физика, управление и кэширование |
| `tests/brick-effects.test.cjs` | Бонусы, кирпичи, комбо, визуальные эффекты и подвижные цели |
| `tests/bosses.test.cjs` | Мультишар, боссы, снаряды и сложные столкновения |
| `tests/persistence.test.cjs` | Контрольные точки, настройки и стресс-регрессии 1.0 RC |
| `tests/browser_smoke.py` | Браузерные проверки разметки, событий, управления и мобильных размеров |

Игра не требует сборщика, npm-пакетов в браузере или API-сервера. Прямое открытие `index.html` остаётся поддерживаемым сценарием. Это ограничение важно учитывать при дальнейшем разделении файлов.

## Ответственность игрового кода

`CFG` хранит постоянные параметры; `LEVELS` — данные секторов. **Не менять физические коэффициенты в ходе структурного рефакторинга:** это изменяет баланс и требует отдельной приёмки.

В классе `Game` логически выделены подсистемы:

1. **Жизненный цикл** — запуск, пауза, переходы секторов, победа/поражение и контрольные точки.
2. **Модель боя** — состояние кирпичей и статистика остаются в `Game`; поведение боссов выделено в `game-bosses.js`, а бонусы и визуальные эффекты — в `game-effects.js`.
3. **Симуляция** — `update(dt)` управляет фазами, а `advancePhysics(dt)` из `game-physics.js` выполняет движение шаров малыми шагами. `updatePaddle`, `updateBoss`, `updateEffectTimers` обновляют остальные сущности.
4. **Столкновения** — методы `moveBall`, `collisionSide` и `reflectBallFromRect` выделены в `game-physics.js`. Для отражения учитываются **предыдущие координаты** шара, чтобы определить грань столкновения. Направленные блоки заранее проверяются на достижимость уязвимой стороны.
5. **Представление** — методы `draw*` из `game-render.js` рисуют Canvas; `game-ui.js` синхронизирует DOM и формирует экраны состояния.
6. **Ввод** — обработчики указателя, клавиатуры и потери фокуса в `game-input.js`.

Рендеринг загружается перед `game.js` и подключается через `Object.assign(Game.prototype, ...)`. В нём нет отдельной копии игрового состояния: методы читают модель в `Game`.

Порядок загрузки: `game-storage.js` → `game-physics.js` → `game-bosses.js` → `game-effects.js` → `game-ui.js` → `game-render.js` → `game.js` → `game-input.js`. Используются последовательные обычные скрипты, а не ES-модули. Прямое открытие `index.html` по `file://` остаётся возможным. В `game.js` остаются состояние кампании и игровой цикл; дальнейшее разбиение имеет смысл только при сохранении простого загрузчика и тестируемой границы подсистем.

## Главный цикл

1. `requestAnimationFrame` вычисляет интервал между кадрами и ограничивает его 33 мс: после сворачивания вкладки игра не должна пытаться симулировать секунды за один кадр.
2. `update(dt)` в состоянии `paused` ничего не изменяет. При игре обновляет часы, эффекты, босса, платформу и активные бонусы.
3. `advancePhysics(dt)` делит интервал на шаги не длиннее 6 мс. Подвижные кирпичи перемещаются **один раз за шаг**, после чего проверяются все активные шары.
4. После симуляции `draw()` формирует кадр; дорогие спрайты и фоновые слои кэшируются.
5. Профилирование включается отдельно (`?fps=1`) и не должно само заметно замедлять обычный режим.

## Сохранения и настройки

`localStorage` содержит независимые ключи рекорда, настроек и контрольной точки. Данные валидируются при чтении, неизвестные версии отвергаются, исключения хранилища не должны блокировать игру.

Контрольная точка создаётся **на границе секторов**: нельзя записывать текущие положения шаров, частично разрушенные кирпичи или состояние незавершённого боя с боссом.

## Проверки и ветки

- Рабочая интеграционная ветка — `develop`; `main` обновляется после завершения приёмки 1.0.
- Запуск: `npm run check`. Он проверяет синтаксис `game.js` и Node-регрессии, разбитые по подсистемам.
- Браузерная проверка: `python tests/browser_smoke.py` после установки Playwright/Chromium.
- До стабильного 1.0 остаётся ручная проверка реального Android, всех пяти секторов, обоих боссов, сохранений и производительности.
- Не удалять исторические ветки, пока их уникальные коммиты и PR не проверены.

## Правила дальнейшего рефакторинга

- Изменения структуры и правил игры вести разными PR: иначе сложно установить причину регрессии.
- Комментарии объясняют **почему** существует ограничение или алгоритм, а не повторяют очевидное присваивание.
- Все новые комментарии, документация и диагностические сообщения — на русском.
- Для изменения физики сначала добавить воспроизводимый тест (угол/скорость/тип кирпича/босс/частота кадров), затем менять реализацию.
- Не считать прохождение CI достаточным доказательством стабильных 60 FPS на физическом телефоне.
