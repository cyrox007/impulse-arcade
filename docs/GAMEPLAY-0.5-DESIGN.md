# «Импульс» — архитектурный план 0.5 («Аномалия сектора»)

**Статус:** проектирование, игровая логика не изменена. Задача: [#19](https://github.com/cyrox007/impulse-arcade/issues/19).

## Зачем

Два постепенных усложнения арканоида:
1. **0.5.0 — подвижные кирпичи**, заставляющие целиться с учётом движения, но без хаоса в мобильном поле.
2. **0.5.1 — мини-босс «Страж ядра»** после очистки третьего сектора, как отдельная финальная фаза.

Текущая версия 0.4.1 остаётся тестовой основой до принятия следующего этапа. Никаких изменений опубликованного `develop` на стадии планирования.

## Что обнаружено в 0.4.1

- `Game.ball` — одиночный объект, `moveBall(dt)` совмещает стенки, платформу и кирпичи.
- `Game.bricks` — массив обычных/бронированных/энергетических/взрывных кирпичей. `drawBricks()` записывается в `brickLayer` только при `bricksDirty`.
- `hitBrick()` удаляет блок и может вызвать `completeLevel()`, когда `bricks.length===0`.
- `blastNeighbors()` определяет соседей по `row/col`; движущаяся цель не должна незаметно менять смысл этих координат.
- Существуют оптимизации 180 частиц / 24 волны и диагностический режим `?fps=1` с временем `update` и `draw`.
- Сквозные тесты предполагают три сектора, один мяч и финальную победу сразу после последнего блока третьего сектора. Эти тесты потребуется целенаправленно обновить.

## Предлагаемая модель данных (не реализация)

```js
// Существующий массив статических кирпичей оставить для совместимости.
game.bricks = [];
game.movingBricks = []; // макс. 3
game.boss = null;       // либо null, либо один Страж
game.sectorPhase = 'bricks'; // 'bricks' | 'guardian' | 'finished'

// Пример объекта, не утверждённый публичный API:
movingBrick = {
  x, y, w: CFG.brickW, h: CFG.brickH,
  minX, maxX, vx, hp: 1, type: 'moving', hitLock: 0
};
```

### Отдельный цикл для движения и коллизий

- Статический слой `brickLayer` не инвалидируется от перемещения динамических объектов.
- Для подвижных блоков предусмотреть предварительно нарисованный спрайт / небольшой кэш; не создавать Canvas-градиенты в каждом кадре.
- Обновление динамических блоков синхронизировать с подшагами `moveBall` (там уже `dt / ceil(dt/.006)`); коллизии шара и перемещающейся цели должны учитывать их положение в одном подшаге.
- Не более трёх движущихся целей. Горизонтальный ход ограничен, без перекрытия стены, платформы и других кирпичей. Простые визуальные подсказки движения.
- При пробивном импульсе: один валидный урон при пересечении цели, защита от повторных срабатываний, пока шар физически внутри AABB.
- Текущие соседние по сетке взрывы применяются **только к `game.bricks`**; подвижные блоки не участвуют в цепной детонации. Если понадобится другое поведение, делать отдельным изменением после тестов.

### Единая точка перехода сектора

Вместо прямой проверки `bricks.length===0` в `hitBrick` предусмотреть `checkStageCompletion()`, вызываемый после любой операции с разрушением блока.

```text
if staticBricks + movingBricks > 0:
    продолжать фазу bricks
else if level == 2 and sectorPhase == bricks:
    sectorPhase = guardian
    создать Стража
else if guardian defeated or level < 2:
    completeLevel() ровно один раз
```

Чтобы избежать дублей, переход в `guardian` сделать идемпотентным; после победы состояние `won` всегда достигается ровно один раз. Статистика финального сектора и награда за жизни выдаются **только после победы над Стражем**.

## Страж ядра — компактная спецификация

- В финале третьего сектора один неподвижный крупный объект в верхней зоне поля. Ориентир — 6 HP, с индикатором оставшихся HP и отчётливым обозначением состояния.
- Две фазовые анимации: **открыт** (можно повредить) и **защищён** (урон не проходит, мяч отражается). Интервалы предварительно 2.5 с и 1.0 с активной игры соответственно; подлежат балансировке.
- Таймер Стража останавливается при паузе и смене видимости страницы. У Стража есть `hitLock`, чтобы одно перекрытие мяча не списывало несколько HP.
- Пробивной импульс может повредить цель во время открытой фазы, но **не должен игнорировать её защитную фазу**. Блокировать бесконечное попадание на одном месте.
- При уроне — собственный энергетический эффект, при уничтожении — короткая особая анимация; использовать общие бюджеты 180 частиц и 24 волн.
- Дополнительные снаряды/лазеры/вражеский урон в первом прототипе **не нужны**: уже есть достаточно новых переходов и столкновений для тестирования.

## План последовательных PR

**PR A — подготовка архитектуры 0.5.0:** `movingBricks`, обновление и отрисовка отдельным слоем, отдельные тесты, без Стража. Переходы секторов в начале не менять, кроме учёта последнего динамического кирпича.

**PR B — 0.5.1 «Страж ядра»:** переход `bricks → guardian → won`, HP и защитная фаза, новые эффекты и UI, сквозные тесты.

**PR C (при необходимости) — полировка:** устранение UX/FPS регрессий, балансировка скорости, длительности фаз и звука по результатам реального Android.

Все PR базируются на актуальном `develop`, каждый проверяется Node и Chromium, `main` не трогается до релизного решения.

## Список проверок

- Существующие **38** Node-тестов должны оставаться зелёными с адаптацией тестов, завязанных на момент победы. Новые: позиция подвижного блока при dt=1/30, 1/60, 1/120; отскок от границы и столкновение; фиксированная пауза; reset.
- Бонусы `shield`, `wide`, `slow`, `pulse` и комбо не меняются неожиданно, потеря мяча и возобновление не теряют фазу.
- Уничтожение последнего подвижного блока не оставляет сектор зависшим; уничтожение последнего статического блока **не** завершает его, если динамический ещё жив.
- Переход в `guardian` и победа проверяются без читерского изменения `state`; тестировать попадания через реальные коллизии.
- Защищённый Страж не теряет HP; уязвимый теряет ровно 1 HP на валидное попадание (или иной отдельно утверждённый урон импульса).
- Отсутствие ошибок JS и появления скрытых кнопок во всех существующих 5 viewport Chromium.
- Кэш статических кирпичей не перерисовывается каждый кадр; динамические спрайты переиспользуются, эффекты имеют ограничения.
- На реальном Android — сравнение третьего сектора со сборкой 0.4.1 при системном потолке 60 FPS, в том числе во время удара по движущемуся кирпичу и Стражу. Пользователю не надо включать 120 Гц.

## Что НЕ входит

- Мультишар: его добавление требует перехода от `ball` к коллекции мячей и проработки последнего потерянного мяча/энергии/барьера/пауз; не включать в 0.5.
- Редактор уровней и пользовательские карты.
- Произвольные дополнительные секторы, которые заставят менять HUD `01/03`.
- Зависимости от новых сторонних JS-библиотек или тяжёлых визуальных шейдеров.

**Зависимость:** 0.4.1 имеет зелёный CI/Pages, но качественное тестирование нового набора эффектов на физическом Android должен подтвердить игрок; до этого нельзя считать 0.5 принятой по производительности.
